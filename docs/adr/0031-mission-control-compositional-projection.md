# ADR-0031 — 3D Mission Control is a derived compositional projection, not an authority

- **Status:** Accepted
- **Date:** 2026-10-02
- **Decision maker:** @ahliweb
- **Related:** ADR-0011 (Control Center and provider boundaries), ADR-0017 (Upstream-first ownership and boundary enforcement), ADR-0023 (Control Center UI/UX design system), ADR-0027 (Control Center secure pull-worker transport), ADR-0028 (Hermes orchestration visualization), ADR-0029 (AI data boundary and private inference), ADR-0030 (GitHub repository progress projection — the closest prior art for an OMES-defined, AWCMS-consumed read projection), [docs/architecture.md §18](../architecture.md#18-layered-reference-architecture-and-deterministic-execution-boundary), [docs/control-center-contracts.md §2.13](../control-center-contracts.md#213-mission-control-scene-view-and-replay-window-issue-264-adr-0031), [docs/ui-ux-design-system.md](../ui-ux-design-system.md), [Issue #247](https://github.com/ahliweb/omes/issues/247), epic [#263](https://github.com/ahliweb/omes/issues/263) and its children [#264](https://github.com/ahliweb/omes/issues/264), [#265](https://github.com/ahliweb/omes/issues/265), [#266](https://github.com/ahliweb/omes/issues/266), [#267](https://github.com/ahliweb/omes/issues/267).
- **Supersedes / Amends:** None. Adds read-only Control Center contracts, a source map, and a guard; does not change any existing contract, operation name, permission, or approval flow.

## Context

Epic #263 asks for a non-redundant 3D Mission Control: an organizational digital twin that shows servers, deployments, jobs, health, backups, Hermes subagents, the architecture, repository progress, AI privacy posture, and pending approvals in one navigable scene, inside the existing AWCMS admin shell.

AWCMS already has, verified on 2026-10-02 against `ahliweb/awcms` `main` (`76f5ded`), exactly 14 `/admin/omes/*` screens (Overview, Servers, Deployments, Operations, Jobs, Health, Backups, Audit, Enrollments, AI Privacy, Live Orchestration, Hermes, Hermes Repository Progress, Architecture; navigation orders 90–103), a canonical workflow-approval inbox at `/admin/approvals`, and one set of action endpoints. The risk of a 3D view is not rendering; it is **redundancy and false authority**: a new "mission" model that competes with jobs, deployments, Hermes sessions, and workflow approvals; a second state vocabulary that drifts from the sources; a second place to approve destructive operations; or a presentation layer whose animation implies state no source ever reported.

The epic's non-redundancy rules therefore require that Mission Control add no authority, no lifecycle, no executor, no approval inbox, and no operation name, and that every object link back to the screen that already owns its detail.

### Constraints

- AGENTS.md §2: OMES owns host/deployment state, Hermes owns agent runtime, AWCMS owns tenant/approval/portal state, GitHub owns repository state. A scene object is a **reference** to one of these, never a copy that can disagree.
- AGENTS.md §3: no arbitrary shell execution, no timeout treated as success, every mutation preflighted, allowlisted, idempotent, audited, and verified. Mission Control must not weaken any of this.
- AGENTS.md §2 (ADR-0017, #247): OMES does not mediate Hermes-native tool execution. Mission Control shows Hermes observations; it never becomes an interception point and Hermes agents stay read-only.
- AWCMS front-end constraints, measured from its repository: Astro with Bun, runtime dependencies only `astro` and `@astrojs/node`, no React, no three.js; a strict CSP (`script-src 'self'` plus one theme-init hash, no `blob:`, no `worker-src`); build gates `PER_FILE_BUDGET_BYTES = 27,000` and `APP_BUDGET_BYTES = 248,033` in `scripts/client-asset-budget.ts` with the measured total at zero headroom; live screens poll with `fetch` (Live Orchestration every 8 s, skipped when `document.hidden`), with no SSE or WebSocket.
- Evidence retained in AWCMS bounds what historical replay can honestly show: Hermes orchestration events (deduplicated, `event_timestamp`), health snapshots (`captured_at`), backup snapshots, jobs (`created_at`/`updated_at`) with worker results (`started_at`/`completed_at`), and workflow decisions are retained; servers, deployments, the architecture snapshot, repository progress, and AI privacy posture are current-only.

This ADR decides the composition architecture, the state and action rules, the replay rules, and renderer guidance. It implements only the OMES-side contract surface (#264).

## Evaluation of Options

| Criterion | **A — Client-side fan-out over existing GET endpoints** | **B — Thin server-side composition with a source map (chosen)** | C — New authoritative "mission"/task domain | D — Persisted scene model with server-stored layout |
|---|---|---|---|---|
| **1. Advantages & disadvantages** | Pro: no new contract; nothing new on the server. Con: the browser makes about ten requests per refresh, composes them inconsistently, and every client re-implements the state mapping. | Pro: one tenant-scoped, bounded, versioned read shape; the mapping lives in one reviewed file; reuses every existing projection. Con: one new composing endpoint in AWCMS and two contracts to maintain. | Pro: a single object model designed for the scene. Con: duplicates jobs, deployments, Hermes sessions, and workflow; two lifecycles that must be reconciled; violates the epic's non-redundancy rules 1–4. | Pro: stable avatar and layout positions across clients. Con: presentation state becomes stored operational truth with no proven cross-client need. |
| **2. Security** | N authorization round-trips with N chances to forget a permission or RLS scope; each client decides what to join; a missing source can silently shrink the scene. | One server-side authorization and RLS pass per request; the response carries references and allowlisted fields only; a version check fails closed; source-map guard MC1–MC9 forbids raw/sensitive terms and unknown operations. | A new write path and lifecycle widens the audit and approval surface, and invites a second executor. | Layout rows are tenant data that must be protected, retained, and migrated for no operational benefit. |
| **3. Performance & resource footprint** | About ten parallel requests per poll; larger client bundle for composition logic against a zero-headroom budget. | One bounded request (nodes at most 500, relations at most 1000); composition cost is server-side and cacheable. | New tables and write amplification. | Extra reads and writes per layout change. |
| **4. Maintainability & code quality** | The state mapping is copied into every consumer and drifts. | One map, one guard; adding a kind, state, relation, or action is a single reviewed change that CI checks against the source contracts. | Two sources of truth to keep consistent forever. | Layout migrations and conflict handling. |
| **5. Scalability** | Fan-out multiplies per-user load on every source endpoint. | Scales with scene size, which is bounded and truncation is reported explicitly. | Scales with a new store. | Scales with users times layouts. |
| **6. Accessibility** | Same as B in principle, but inconsistent snapshots make the accessible list and the 3D view disagree. | One consistent snapshot feeds both the 3D view and the mandatory synchronized object list. | Same, over a model users must learn. | Same. |
| **7. SEO** | Not applicable: authenticated admin-only screen. | Not applicable. | Not applicable. | Not applicable. |
| **8. UI/UX implications** | Partial loads and mixed instants make the scene look inconsistent. | One snapshot instant (`as_of`), explicit per-source availability, explicit truncation. | A "mission" concept operators must learn alongside jobs and deployments. | Users could rearrange objects, but position carries no meaning and can mislead. |
| **9. Compatibility** | Breaks silently when any source endpoint changes. | Versioned (`schema_version`, `source_map_version`); consumers reject unknown major versions; fits the existing SHA-256 vendoring pin. | Requires migration of existing records into the new model. | Same as C for layout data. |
| **10. Operational complexity** | No new server code, but hard to debug a scene composed differently on every client. | One endpoint and one map; the guard runs in `scripts/check-architecture.py`. | A new lifecycle to monitor, back up, and reconcile. | New table, retention, and backup scope. |
| **11. Long-term implications** | Rework once a second consumer or replay arrives. | Extends additively (new kinds go through the map first); keeps AWCMS presentation separate from every authority. | Entrenches a competing domain model and splits operator attention. | Entrenches presentation as data, hard to remove. |

## Decision

We adopt **Option B**: **3D Mission Control is a derived presentation/read-model composition, not a new authority.** AWCMS assembles a tenant-scoped `mission-control-scene-view` (references plus bounded label, state, freshness, and detail-route fields only) and bounded `mission-control-replay-window` pages from its existing directories. A version-controlled `contracts/control-center/v1/mission-control-source-map.json` is the single anti-redundancy map. For every object kind it records its one authority, source contract, opaque id field, freshness basis, allowed fields, canonical detail route, candidate **existing** actions, replay basis, and deterministic state map. The OMES guard MC1–MC9 in `lib/omes/py/architecture/mission_control.py`, run by `scripts/check-architecture.py`, keeps the map consistent with the contracts it references:

| Guard | Checks |
|---|---|
| MC1 | Source-map shape (required keys, kind keys, state-map values, replay bases) |
| MC2 | Kinds, sources, relations, visual states, and versions are in bijection with the two schemas |
| MC3 | Every referenced source contract exists under `contracts/control-center/v1/` |
| MC4 | Every state value of every referenced source contract is mapped (anti-drift: a new upstream state fails CI until it is classified) |
| MC5 | Detail routes are limited to the 14-screen inventory plus `/admin/approvals`; the workspace replaces no screen |
| MC6 | Relation endpoints are known kinds |
| MC7 | Candidate actions resolve to existing paths; `operation.*` actions are members of the `operation-request` operation enum only |
| MC8 | Every valid fixture's `visual_state` equals the deterministic derivation |
| MC9 | Forbidden raw/sensitive field terms never appear in allowed fields |

The following rules are part of the decision.

1. **`visual_state` is deterministic.** The base class is `state_map[kind][source_state]`, and an unmapped value is `unknown`. Freshness `unknown` gives `unknown`; freshness `stale` keeps `failed` or `warning` (a last-known problem never disappears) and otherwise gives `stale` (a last-known success is never shown as current). It is never inferred from animation. Hermes subagents use only their eight v1 states (`PENDING`, `STARTING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `INTERRUPTED`, `CANCELLED`, `UNKNOWN`); no reasoning or hidden state is displayed.
2. **Freshness budgets reuse existing AWCMS constants.** Server 300 s (`STALE_HEARTBEAT_THRESHOLD_MS`); deployment 1800 s (`STALE_RECONCILIATION_THRESHOLD_MS`); a non-terminal job inherits its target server's heartbeat freshness (300 s) and terminal job states never go stale; Hermes orchestration 120 s (`DEFAULT_TREE_FRESHNESS_WINDOW_SECONDS`); backup 86400 s (`BACKUP_FRESHNESS_THRESHOLD_MS`); repository progress 1800 s (the 15-minute poll interval times grace multiplier 2). **Health snapshots are a new rule:** AWCMS has no existing health staleness rule, so this ADR introduces a documented Mission Control budget of 1800 s on the latest `captured_at`. The architecture snapshot, AI privacy posture (which uses its own `evidence_freshness` field), and workflow approvals have no time budget.
3. **Action availability is not in the scene contract; it is a separate advisory actions endpoint.** AWCMS computes it server-side per selected object at selection time from existing permission and capability evidence and serves it from its own `GET /api/v1/omes/mission-control/actions?kind=&id=` endpoint, never as a scene field, and every mutation goes through the existing endpoint with the same `Idempotency-Key`, audit record, and workflow approval: `POST /api/v1/omes/operations`, `POST /api/v1/omes/jobs/{id}/cancel`, `POST /api/v1/omes/jobs/{id}/approve`, and `POST /api/v1/omes/backups/{id}/restore`. (`POST /api/v1/omes/ai-privacy/egress-approvals` also exists but is not a Mission Control candidate action; the AI privacy node is read-only.) Approval decisions are made only in the canonical `/admin/approvals` inbox (OMES destructive operations and backup restore start a workflow instance under `omes_control.destructive_operation`). Hermes agents are read-only. No new operation name is introduced, and there is no global "kill all AI" action.
4. **Historical mode is bounded and honest.** Replay-window pages hold at most 500 events with a cursor; events are deduplicated by `(evidence_kind, evidence_id)` and ordered by `(at, evidence_kind, evidence_id)`; late arrivals are labelled `late_arrival`; gaps are explicit (`not_retained`, `retention_expired`, `source_unavailable`, `before_first_observation`) and never interpolated. The replay basis per kind is `event_log` (Hermes orchestration events), `snapshot_series` (health and backup snapshots), `terminal_transitions` (jobs with worker results, and workflow decisions), or `current_only` (servers, deployments, architecture, repository progress, AI privacy posture; shown with an evidence gap, never back-dated). Mission Control extends no retention. Historical mode exposes no actions.
5. **No new capability-registry entry.** Mission Control adds no authority, and `architecture/capabilities.json` records authorities (it has no entries for the other AWCMS views either), so it is unchanged. This avoids a second registry.
6. **Renderer guidance for #265 (measured and confirmed in the AWCMS PR; see "Consumption (shipped)").** A minimal hand-written WebGL2 renderer bundled same-origin is preferred over three.js (a three.js build is hundreds of KB minified, far over the 27,000-byte per-file budget and the zero-headroom app budget, and adds a supply-chain and update surface) and over React or React Three Fiber (not used by AWCMS). WebGL2 is the baseline; WebGPU is deferred. Geometry is procedural and low-poly; no remote assets or CDN; no `blob:` workers under the current CSP. Any budget raise must be measured and justified in `scripts/client-asset-budget.ts`, never silent, and the CSP is never weakened for WebGL. A synchronized accessible object list and a no-WebGL fallback are mandatory, and the existing 2D screens remain the canonical detail views.
7. **Rejected alternatives** (see the matrix): (A) client-side fan-out, rejected for N authorization round-trips, inconsistent snapshot instants, per-client re-implementation of the state mapping, a larger client bundle against a zero-headroom budget, and a harder fail-closed version check; (C) a new authoritative "mission"/task domain, rejected because it competes with jobs, deployments, Hermes sessions, and workflow and violates the epic's non-redundancy rules; (D) a persisted scene model with server-stored avatar/layout coordinates, rejected because presentation state would become false operational truth with no proven cross-client need.

## Standards alignment (engineering, not certification)

This design is aligned with the following references as an engineering input. It is **alignment, not a certification claim**: no audit, attestation, or certification against any of these is made or implied.

| Reference | How the design aligns |
|---|---|
| ISO/IEC 27001 / 27002 | Access control (server-side authorization per request, default-deny permissions), logging (existing audit and correlation records), secure development (guard MC1–MC9 in CI, fixtures including an injection case) |
| ISO/IEC 27005 | Risk handling recorded as threats CC11–CC19 in [docs/control-center-threat-model.md](../control-center-threat-model.md) |
| ISO/IEC 27017 / 27018 | Cloud service and PII protection: single-tenant composition, RLS on every source query, no personal data beyond what the source screens already show |
| ISO/IEC 27034 | Application security controls encoded as testable constraints (allowed fields, forbidden terms, bounded sizes, output encoding) |
| ISO/IEC 27701 | Privacy: data minimization by allowlist, no new store of personal data, no retention extension |
| ISO/IEC 20000-1 | Service management visibility: one consistent view of service state with explicit freshness and source availability |
| ISO 22301 | Continuity: the no-WebGL fallback and the unchanged 2D screens keep operations possible when the workspace is unavailable |
| ISO/IEC 42001 and NIST AI RMF | AI oversight: Hermes activity is shown as observed state only, with no hidden reasoning, prompts, or transcripts, and agents stay read-only |
| NIST SP 800-207 | No implicit trust: per-request authorization and re-authorization of every action; the scene grants nothing |
| OWASP ASVS and API Security Top 10 | Output encoding, bounded inputs and pagination, object-level authorization, no mass assignment, no unsafe consumption of upstream data |
| Indonesian UU 27/2022 (PDP) and PP 71/2019 | Personal data protection and electronic system operation: minimization, access control, and auditability inherited from the source screens |

The generic contract validator test already requires a valid and an invalid fixture per schema.
- AWCMS re-vendors these files through its SHA-256 pin (`contracts:omes:sync`), done in #265. Editing the vendored copy is drift, not a fix (AGENTS.md §5).
- [docs/control-center-contracts.md](../control-center-contracts.md) §2.13, [docs/control-center-and-integrations.md](../control-center-and-integrations.md), [docs/ui-ux-design-system.md](../ui-ux-design-system.md), [docs/control-center-release-closeout.md](../control-center-release-closeout.md), [docs/control-center-threat-model.md](../control-center-threat-model.md), [docs/architecture.md](../architecture.md), and [docs/security.md](../security.md) are updated in the same change. Stale claims about the enrollment-token screen (shipped under #233, `ahliweb/awcms` PR [#825](https://github.com/ahliweb/awcms/pull/825), merged as `eff72e87`) and the screen count are corrected so the inventory reads as the 14-screen baseline.
- **AWCMS consumption: shipped** (#265, #266, #267): `ahliweb/awcms` PRs [#880](https://github.com/ahliweb/awcms/pull/880) (squash `953414f`), [#881](https://github.com/ahliweb/awcms/pull/881) (squash `3c239ca`), and [#882](https://github.com/ahliweb/awcms/pull/882) (squash `27e62b3`). See "Consumption (shipped)" below and [docs/control-center-release-closeout.md](../control-center-release-closeout.md) §6.2. This ADR's own OMES contract surface (#264) ships in OMES PR [#268](https://github.com/ahliweb/omes/pull/268), which is **pending merge (approval required)**; no merge commit is recorded yet.
- Adding a scene object kind, state value, relation, or action later requires a change to the source map first (guard MC1–MC9), a mapping to an existing authority and canonical 2D route, and never a new executor, approval inbox, or operation name.
- Residual risk: the guard proves the map is consistent with the OMES-side contracts; it cannot prove that the AWCMS composition honors tenant isolation, output encoding, or server-side action authorization. Those are acceptance criteria for #265 and #267 and were evidenced there (see below) (cross-tenant integration tests, an encoding test using the `<img onerror>` fixture, and the measured client-asset budget).

A prerequisite dependency-override fix for high advisories in `devalue` and `undici` (`ahliweb/awcms` PR [#879](https://github.com/ahliweb/awcms/pull/879), `c525749`) was found while validating and is not an OMES issue.

- **Composition (#265).** `/admin/omes/mission-control` (navigation order 104) is guarded by the existing `omes_control.servers.read`; no new permission, table, or migration. `GET /api/v1/omes/mission-control/scene` composes server-side from the existing directories with per-source read gating through `authorizeInTransaction`: an unreadable source is reported `unavailable` and is never queried. The response is schema-validated and fails closed. This is Option B as decided.
- **Renderer decision confirmed.** A hand-written WebGL2 renderer, loaded as a lazy `scene-gl` chunk, with no three.js and no React, as rule 6 preferred. The accessible server-rendered object list is the canonical non-3D view and works without JavaScript or WebGL. The HUD is an `aria-live` region, keyboard navigation is supported, selection is carried in the URL (`?kind=&id=`), reduced motion is honoured, and polling is 15 s and visibility-aware; a missed refresh window ages the retained scene to stale (`ageOutScene`), so a last-known success is never shown as current (rule 1).
- **Measured client budgets** (each raise is measured and recorded in `scripts/client-asset-budget.ts` in AWCMS, never silent, as rule 6 requires). `APP_BUDGET_BYTES` 248,033 to 275,629 for the workspace (+27,596 B), to 286,415 for history mode (+10,786 B), and to 295,244 for contextual actions (+8,829 B). Per-chunk sizes: page script 15,488 B at #265, later 17,921 B with the replay and actions hooks; `scene-gl` 9,651 B; replay chunk 7,764 B at #266, later 7,663 B; actions chunk 6,819 B. All stay under the 27,000-byte per-file budget.
- **History mode (#266).** `GET /api/v1/omes/mission-control/replay?from&to&cursor` (window at most 24 h, at most 500 events per page, keyset cursor, unknown parameters rejected 400) and `?as_of=` on the scene route. Events are deduplicated by `(evidence_kind, evidence_id)` in deterministic order; `late_arrival` is page-local. Gaps are explicit and come from the module's data-lifecycle descriptors (health 30 d, jobs 60 d, backups and Hermes events 90 d, worker results 730 d); workflow instances are not purged, so their gap is `before_first_observation`. `current_only` kinds are never back-dated. `sql/168` is index-only on OMES tables; the workflow module's table is deliberately not indexed (a read exception only). 47 PostgreSQL integration tests cover it.
- **Actions (#267), as corrected in rule 3.** Availability is served by the separate advisory `GET /api/v1/omes/mission-control/actions?kind=&id=` endpoint (strict parameters; `not_found` for an unknown, other-tenant, or unreadable-source target, so there is no existence oracle) and is never part of the scene contract. It mirrors exactly what the existing endpoints enforce (`job.cancel` for a queued job, `job.requeue` for a failed job, and permissions). Mutations call only the four existing endpoints (`operations`, `jobs/{id}/cancel`, `jobs/{id}/approve`, `backups/{id}/restore`) with the canonical body and row-id path, one `Idempotency-Key` per intent, the shared `ConfirmDialog`, and a preflight summary. Outcomes are `accepted`, `approval_required`, `rejected`, or `unknown`; acceptance is never shown as success. Approvals are made only through a link to `/admin/approvals`. An opt-in `data-command-palette-item` hook feeds the AWCMS admin command palette. Forged-POST integration tests assert 403/404 with state unchanged.
- **Advisories versus enforcement.** A stale target, a decommissioned target, and an unverified backup are non-blocking advisories because the canonical endpoints do not enforce them; the advisory endpoint does not invent a stricter rule than the endpoint it fronts. A possible follow-up would enforce them in the canonical endpoints. That is a proposal, not tracked by a numbered issue.
- **Vendored contracts.** AWCMS pins the OMES contracts to commit `a4026e6` (the #268 head) and will re-pin to #268's squash SHA after it merges (identical content).
