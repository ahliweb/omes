# ADR-0030 — GitHub Repository Progress Projection for the Progres Hermes View

- **Status:** Accepted
- **Date:** 2026-09-27
- **Decision maker:** @ahliweb
- **Related:** ADR-0011 (Control Center and provider boundaries), ADR-0017 (Upstream-first ownership and boundary enforcement), ADR-0027 (Control Center secure pull-worker transport), ADR-0028 (Hermes orchestration visualization — the closest prior art for an OMES-defined, AWCMS-consumed read projection), ADR-0029 (AI data boundary and private inference), [docs/control-center-and-integrations.md](../control-center-and-integrations.md) §8, [docs/domain-providers.md](../domain-providers.md) §4, [docs/control-center-contracts.md](../control-center-contracts.md), [Issue #249](https://github.com/ahliweb/omes/issues/249), split from [Issue #246](https://github.com/ahliweb/omes/issues/246) part 2.
- **Supersedes / Amends:** None. Adds a new read-only Control Center contract and fetch-path decision; does not change the GitHub App installation/webhook-envelope/observation contracts issue #101 already defined (`contracts/domains/v1/github-*.schema.json`, `lib/omes/py/domains/github.py`).

---

## Context

The OMES Control Panel redesign adds a **Progres Hermes** view: milestone name, done/open issue counts and percentage, plus issue number, title, state, and kind, for the `ahliweb/omes` repository (and, per-tenant, whichever repository a tenant configures). Issue #246 part 2 shipped this view only as an explicit empty state that links to this issue, because:

- GitHub is the authority for repository, workflow, release, and deployment observations (AGENTS.md §2); OMES/AWCMS must not maintain a second, hand-edited copy of that state.
- No `contracts/control-center/v1/` schema covered milestone/issue progress before this ADR.
- Issue #101 already defined the GitHub App installation, repository/environment mapping, webhook-envelope, and generic `github-provider-observation` contracts (`contracts/domains/v1/`) plus a stdlib HMAC-SHA256 webhook verifier (`lib/omes/py/domains/github.py`), but never a Control-Center-facing progress *view*, and never a decision on which system fetches the data.

This ADR decides only the fetch path and the wire contract (`repository-progress-view.schema.json`) for that view. It does not implement the AWCMS-side polling job, screen, or database — see "AWCMS consumption expectations" below for what remains open, tracked in #249.

### Constraints

- No write scopes on GitHub — this is a read-only progress board, not a mutation surface.
- No inbound privileged OMES listener (ADR-0027 still applies if any inbound delivery is ever added).
- No issue bodies, comments, or assignee/author PII beyond what a progress board needs (AGENTS.md §3, §5).
- A stale observation must be rendered as stale, never silently presented as current (the same freshness discipline as `docs/control-center-contracts.md` §2.9's projection-state pattern).

## Evaluation of Options

| Criterion | **A — AWCMS polls GitHub REST API (chosen)** | B — GitHub webhooks | C — OMES host worker fetches | D — Static committed snapshot |
|---|---|---|---|---|
| **1. Advantages & disadvantages** | Pro: simple, stateless, no public inbound surface, works for any tenant-configured repository without per-repo webhook setup. Con: bounded freshness (poll interval), consumes API quota. | Pro: near-real-time updates. Con: needs a public inbound HTTP endpoint, signature/replay handling (even reusing the existing verifier), and backfill still needs polling for gaps/initial population and for repositories added after the fact. | Pro: reuses OMES's existing outbound pull-worker transport. Con: OMES is host control (deterministic plane); a GitHub repository observation is not host state, and mediating it through OMES adds a hop with no security or freshness benefit. | Pro: trivial to implement. Con: immediately stale, and every refresh requires a code change/deploy — the definition of "a false copy of provider truth" AGENTS.md §3 prohibits. |
| **2. Security** | Read-only REST calls; optional read-only fine-grained token or GitHub App installation token via `secret_reference` only, never a raw value; unauthenticated works for public repositories (see "Authentication" below). No new inbound attack surface. | Requires a public inbound endpoint, HMAC signature verification, and replay protection (issue #101 already built the primitive, `lib/omes/py/domains/github.py`, but a live receiver is a new production attack surface: DoS, spoofed deliveries, endpoint discovery). | Adds a second system (OMES) that must also hold a GitHub credential, doubling the credential-exposure surface for no capability gain. | No live credential exposure, but "secure because it does nothing" is not a security property worth having, given #1/#4. |
| **3. Performance & resource footprint** | One REST call per repository per 15-minute interval (default); unauthenticated GitHub REST allows 60 requests/hour per originating IP, which comfortably covers one repository at a 15-minute cadence (4 requests/hour) with headroom for several more; conditional requests (ETag/`If-None-Match`) keep a no-change poll cheap and, per GitHub's documented behavior, do not count against the rate limit. | Lower steady-state load (event-driven), but requires a durable delivery-processing pipeline (queue, retry, dedupe) that this design does not otherwise need. | Same network cost as A, plus an extra internal hop (Control Center to OMES to GitHub, then back) that adds latency and a new failure mode. | Zero runtime cost, and zero runtime value. |
| **4. Maintainability & code quality** | One polling job, one schema, one freshness rule; no new inbound transport to maintain. | Reuses the existing HMAC verifier (good), but adds an inbound HTTP receiver, delivery-ID storage, and replay-window configuration that do not exist in this repository today and are out of scope for #249. | Would require exposing a new OMES-side "fetch arbitrary GitHub data" capability, which has no other consumer and blurs OMES/AWCMS authority (AGENTS.md §2). | A committed snapshot needs manual updates forever; it is a maintenance liability, not a reduction of one. |
| **5. Scalability** | Scales linearly with tenant/repository count by adding polling jobs; GitHub's per-installation or per-token rate limits (5,000/hour authenticated) scale far beyond what a 15-minute cadence needs even across many repositories. | Scales well per event, but the receiver, queue, and replay-window state must scale with delivery volume across all installations — infrastructure this repository does not have a home for. | Inherits A's scaling profile plus an added OMES-side fan-out concern. | Does not scale — every additional repository is a manual edit. |
| **6. Accessibility** | No UI impact by itself; the freshness/stale state this ADR requires gives the eventual AWCMS screen an explicit, announceable status rather than silently wrong data. | Same. | Same. | Same, but the underlying data is never trustworthy enough for an accessible status to be meaningful. |
| **7. SEO** | None — this is an admin-only, authenticated Control Center screen; not applicable. | None. | None. | None. |
| **8. UI/UX implications** | The screen can show real milestone/issue progress with a visible `observed_at`/freshness indicator, or an explicit unconfigured/stale/error state — never a silent guess. | Same end-state UX as A once backfill polling is added anyway, at higher implementation cost. | Same end-state UX as A, at higher architectural cost. | Data drifts silently from GitHub with no user-visible signal short of noticing the numbers are wrong. |
| **9. Compatibility** | Works identically for any GitHub-hosted repository a tenant configures, with or without a GitHub App installation. | Only works for repositories where a webhook has been registered and the receiver is reachable — a heavier precondition than issue #249 needs for a first iteration. | Requires OMES to be network-reachable to GitHub from every host, which is not guaranteed and is not otherwise a requirement of OMES's host-control role. | Compatible with nothing that changes. |
| **10. Operational complexity** | One scheduled job per tenant/repository, no new listener, no new queue. | A production webhook receiver needs monitoring, secret rotation, replay-window tuning, and incident response for delivery failures — real operational weight for a "nice to have sooner" freshness gain. | Adds a cross-system dependency (AWCMS to OMES to GitHub) for a capability that does not need OMES at all. | Lowest day-to-day complexity, highest correctness risk. |
| **11. Long-term implications** | Keeps GitHub as the sole authority, AWCMS as the sole consumer/projector, and OMES entirely out of a plane it does not own (AGENTS.md §2's "AWCMS ... must never execute arbitrary host shell commands" cousin: OMES must not become a generic outbound fetch proxy for AWCMS either). Webhooks remain available later as an additive freshness optimization without changing this contract's shape. | A reasonable **future optimization**, not a foundation: adopting it later only shortens the freshness window on top of A, it does not replace the need for A's backfill/reconciliation poll. | Sets a precedent that OMES mediates arbitrary provider API calls on AWCMS's behalf, contradicting the layered reference architecture (docs/architecture.md §18) and inviting scope creep into a second, informal API gateway. | Guarantees increasing drift and an eventual trust failure in the displayed data. |

## Decision

We adopt **Option A**: **AWCMS polls the GitHub REST API** on a schedule (default: every 15 minutes), read-only, producing a tenant-scoped `repository-progress-view` projection.

1. **Authentication is optional**, resolved per tenant/repository:
   - **None** for a public repository. GitHub's unauthenticated REST rate limit (60 requests/hour per originating IP) comfortably covers a 15-minute polling cadence.
   - **A read-only fine-grained personal access token, or a GitHub App installation token**, referenced by `secret_reference` (`{"store": "env"|"file"|"vault"|"os-keyring", "key": "..."}`) — never a raw token value anywhere in a request, response, log, fixture, or database row (`docs/control-center-contracts.md` §4). A configured token raises the effective rate limit to 5,000 requests/hour and allows private repositories.
2. **No write scopes are ever requested or used.** This is a read-only observation path; it must not be combined with issue #101's `deployments:write` installation permission for any mutation.
3. **`repository-progress-view.schema.json`** (`contracts/control-center/v1/`) is the wire shape AWCMS's polling job produces and the Control Center screen consumes: `schema_version`, `tenant_id`, `repository` (`owner`, `name`, `html_url` restricted to `https://github.com/`), `observed_at`, `source` (`github_rest_poll`, with `github_webhook` reserved — see below), `milestones[]` (number, title, state, open/closed issue counts, `due_on`, `html_url`), and `issues[]` (number, title, state, label names only, `milestone_number`, a derived `kind`, `html_url`, `updated_at`). It carries no issue bodies, no comments, and no assignee/author PII. `additionalProperties: false` at every object level makes "no raw shell/command escape hatch anywhere in this schema" structural (registry guard C1), matching every other `contracts/control-center/v1` schema.
4. **`kind` is derived deterministically from labels, never invented**: `type:epic` → `epic`; `type:feature` or `enhancement` → `feature`; `bug` or `type:bug` → `bug`; `documentation` or `type:documentation` → `docs`; anything else → `other`. This mapping lives in this ADR and in `docs/control-center-contracts.md`; the actual derivation code is AWCMS's, since AWCMS is the system doing the polling and projecting (see "AWCMS consumption expectations").
5. **`source: "github_webhook"` is reserved, not implemented.** It exists in the enum now so that a later, additive optimization — a webhook delivery that refreshes a projection sooner than the next poll, reusing the existing `lib/omes/py/domains/github.py` HMAC-SHA256 verifier and issue #101's `github-webhook-envelope` contract — does not require a breaking schema change. Per the evaluation above, a webhook alone is never sufficient (backfill and initial population still need polling), so this reservation does not change the decision.
6. **Rejected alternatives** (see the matrix): (B) webhooks alone, for the reasons above, kept as a possible later *additive* optimization only; (C) an OMES host worker fetching GitHub data, rejected as the wrong authority plane — repository progress is a GitHub observation consumed by AWCMS, not host-control state OMES owns, and OMES must not become a generic outbound fetch proxy for AWCMS; (D) a static committed snapshot, rejected as a stale, false copy of provider truth that AGENTS.md §3 already prohibits in spirit.
7. This fits the existing issue #101 GitHub observation model: GitHub is the authority, AWCMS stores observations stamped with `observed_at`, and a stale observation renders as stale rather than as current.

## Consequences

- A new versioned contract, `repository-progress-view.schema.json`, plus fixtures (`contracts/control-center/v1/fixtures/repository-progress-view/`) and a validator test (exercised generically by `tests/py/contracts/test_check_contracts.py`, which requires every schema to have at least one valid and one invalid fixture) are added by this ADR's owning PR.
- No OMES-side Python module is added for this capability: OMES's contribution is the contract only. The polling job, the label→`kind` derivation, the projection table, and the screen are entirely AWCMS's responsibility (`ahliweb/awcms`, not this repository, per AGENTS.md §5's Control Center ownership rule).
- `docs/control-center-and-integrations.md` §8 and `docs/control-center-contracts.md` are updated to reference this contract as the first concrete consumer of the GitHub observation model issue #101 defined.
- `architecture/capabilities.json` gains one new entry, `provider.github.repository_progress` (plane `business_control`, authority `provider`, execution_semantics `external_authority`, `implementation_status: staged`, `omes_module: null`, `adr_reference: "ADR-0030"`), and the checked-in `architecture-capabilities-view` fixture is regenerated so registry guard AV1 stays green.
- **AWCMS consumption: Not implemented yet (tracked in #249).** No polling job, projection table, or `/admin/omes/*` screen exists in `ahliweb/awcms` as of this ADR. The remainder of this section records what that future implementation must satisfy, so the contract accepted here is not reopened for renegotiation later.

### AWCMS consumption expectations (not implemented yet; tracked in #249)

- **Polling job**: a scheduled job per tenant/repository (default interval: 15 minutes, operator-configurable), reading `secret_reference` if configured, calling the GitHub REST API for milestones and issues, and writing a `repository-progress-view`-shaped row.
- **Projection table with FORCE RLS**: the projection table must enforce row-level security (`FORCE ROW LEVEL SECURITY`) scoped by `tenant_id`, matching this repository's existing Control Center tenant-isolation expectations (`docs/control-center-contracts.md` §1) — never relying on application-layer filtering alone.
- **Freshness semantics**: the screen compares `observed_at` against the configured poll interval (plus a grace window) to decide fresh vs. stale, the same pattern as `docs/control-center-contracts.md` §2.9's `projection-state` `freshness.stale` field.
- **Explicit unconfigured / stale / error states**: the screen must render three distinguishable states — no repository configured for this tenant, a configured repository whose last successful poll is older than the freshness threshold ("stale," with the last `observed_at` shown), and a poll that is currently failing ("error," with the last successful `observed_at` retained rather than discarded) — never silently falling back to empty or to stale data presented as current.
- **Rate-limit and quota discipline**: the polling job must use conditional requests (`ETag`/`If-None-Match`) so an unchanged repository's poll does not consume additional GitHub rate-limit quota (per GitHub's documented conditional-request behavior), and must back off (without crashing the schedule) when it does exhaust its quota, surfacing that as the "error" state above rather than retrying in a tight loop.
- **No write scopes**: the token or App installation used, if any, must never be granted a scope broader than read access to metadata/issues/contents; this is a read-only progress board.
