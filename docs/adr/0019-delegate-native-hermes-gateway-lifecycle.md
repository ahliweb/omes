# ADR-0019: Delegate Native Agent Deployment Lifecycle to Hermes CLI

- Status: Accepted
- Date: 2026-09-21
- Related issues: [#175](https://github.com/ahliweb/omes/issues/175), [#174](https://github.com/ahliweb/omes/issues/174), [#176](https://github.com/ahliweb/omes/issues/176), [#177](https://github.com/ahliweb/omes/issues/177)

## Context

In upstream Hermes Agent (`v2026.9.14`), multi-profile gateway deployment and lifecycle management are natively supported through the `hermes gateway` CLI (`hermes gateway install`, `hermes gateway start`, `hermes gateway stop`, `hermes gateway restart`, `hermes gateway status`). Upstream manages unit creation under the standard convention:
- `hermes-gateway.service` for the default profile;
- `hermes-gateway-<profile>.service` for distinct named profiles;
- or a single multiplexed gateway process serving multiple profiles concurrently.

Previously in OMES, the agent deployment engine (`lib/omes/py/agent/cli.py`, `plan.py`, `unitfile.py`) generated and wrote complete standalone systemd service unit files named `omes-agent-<name>.service`. This implementation had several drawbacks:
1. **Capability Duplication**: Duplicated systemd unit templating and service lifecycle logic already provided by upstream Hermes, violating ADR-0017 (`DELEGATE -> PORT -> ADAPT -> DEFER -> REJECT`).
2. **Dual-Process Risk**: If an operator or tool used both OMES and `hermes gateway`, two systemd services could run simultaneously polling the same bot tokens or accessing the same session sqlite databases.
3. **Drift from Upstream Updates**: Upstream changes to `hermes gateway` flags, environment setups, or daemon behavior required manual updates to OMES's internal template generator.
4. **Unclean Separation on Rollback**: Rolling back an OMES deployment destroyed the unit file rather than returning the service to native upstream control or cleanly detaching host resource overlays.

## Evaluation of Architectural Options

### Option 1: Continue generating standalone `omes-agent-<name>.service` unit files in OMES
- **Pros**: Retains existing unit file templates; zero changes to unit naming.
- **Cons**: Duplicates upstream Hermes gateway functionality; risks concurrent unit execution; creates maintenance overhead as Hermes gateway flags evolve.
- **Security**: Medium; risks race conditions if multiple services poll the same Telegram bot token or credential store.
- **Maintainability**: Poor; violates ADR-0017 upstream-first delegation.
- **Long-term Technical Implications**: Blocks seamless alignment with upstream multi-agent features and monitoring.

### Option 2: Direct Hermes gateway invocation with full file takeover (overwriting upstream unit files)
- **Pros**: Uses Hermes service names.
- **Cons**: Overwriting files generated by `hermes gateway install` creates conflicts on upstream updates; rollback would delete files created by upstream tools.
- **Operational Complexity**: High; fragile file ownership boundaries.

### Option 3: Upstream-First Delegation with Drop-in Resource Overlays and Legacy Migration (Chosen)
- **Pros**:
  - **Crisp Authority Separation**: Upstream Hermes owns base service unit generation and process execution (`hermes gateway install/start/stop/restart/status`). OMES owns host compatibility, placement, cgroup resource quotas (`MemoryMax`, `CPUQuota`, `TasksMax`), and host hardening.
  - **Non-Invasive Overlays**: OMES attaches resource quotas exclusively via systemd drop-in overlays (`<unit>.d/10-omes-agent-resources.conf`), never modifying upstream unit files directly.
  - **Clean Rollback**: Rollback removes *only* OMES-managed drop-in overlays (`managedPaths = [dropin_path]`), stops the service via `hermes gateway stop`, and leaves upstream unit files and Hermes profile data intact.
  - **Safe Migration**: Automatically discovers and cleans up legacy `omes-agent-<name>.service` units and old drop-in directories, stopping and disabling them before activating the upstream service to avoid dual polling.
  - **Topology Awareness**: Detects standalone profile services vs single multiplexed gateways (`SHIM_HERMES_MULTIPLEXED=1` or `hermes gateway status`), suppressing redundant service installation when a multiplexed gateway already serves the profile.
- **Advantages and Disadvantages**: Fully delegates agent service generation while preserving OMES host governance; requires migrating legacy unit names.
- **Security**: Eliminates dual-process credential polling and ensures cgroup limits and systemd sandbox directives are cleanly layered over the upstream process.
- **Performance**: Near-instantaneous apply; utilizes native systemd drop-in evaluation without template recompilation overhead.
- **Maintainability**: Eliminates duplicate unit file generation code; aligns unit lifecycle directly with upstream Hermes releases.
- **Scalability**: Seamlessly supports multi-profile agent topologies, including dedicated profile units and multiplexed daemon processes.
- **Accessibility & UI/UX**: Machine-readable JSON output for `plan`, `apply`, `status`, and `rollback` provides clear visibility into upstream unit names, active states, and multiplexed mode.
- **SEO & Web Impact**: Not applicable directly to backend service daemons; ensures consistent service health reporting for control center APIs.
- **Compatibility**: Compatible with systemd user manager on Ubuntu 24.04/26.04 and Linux Mint 22.x, as well as system scope where designated.
- **Operational Complexity**: Low; fully automated migration of legacy units during `omes agent apply`.
- **Long-term Technical Implications**: Prepares the runtime boundary for `hermes doctor` integration (issue #176) and unified state management (issue #177).

## Decision

1. **Service Unit Derivation and Naming**:
   - `lib/omes/runtime.sh` (`runtime_agent_service_unit`) and `lib/omes/py/agent/plan.py` (`unit_name`) derive:
     - `hermes-gateway.service` for profile `default`;
     - `hermes-gateway-<profile>.service` for any other named profile.
   - `legacy_unit_name(agent_name)` derives `omes-agent-<name>.service`.

2. **Base Unit Ownership & Drop-in Overlay**:
   - Base service unit files are installed exclusively by `hermes gateway install [--profile <profile>]`.
   - OMES generates and manages *only* the drop-in overlay file `<unit_dir>/<unit_name>.d/10-omes-agent-resources.conf`.
   - `managedPaths` recorded in deployment state contains only the drop-in overlay path.

3. **Lifecycle Command Delegation**:
   - `apply`: Runs `hermes gateway install` (if not multiplexed), writes the drop-in overlay, executes `daemon-reload`, starts via `hermes gateway start` / `systemctl enable --now`, and verifies active status.
   - `restart`: Invokes `hermes gateway restart` with fallback to `systemctl restart`.
   - `stop`: Invokes `hermes gateway stop` with fallback to `systemctl stop`.
   - `rollback`: Stops the service via `hermes gateway stop`, disables via systemctl, unlinks only the drop-in overlay, reloads systemd daemon, and verifies the drop-in is gone while preserving the base unit and Hermes profile data.
   - `status`: Queries `hermes gateway status` and systemctl `is-active`, reporting `unitActive` and `multiplexed` mode flag when active.

4. **Legacy Unit Migration**:
   - When applying an agent, OMES inspects the unit directory for `omes-agent-<name>.service` and `omes-agent-<name>.service.d/`.
   - If present or active, OMES stops and disables the legacy unit, deletes the legacy unit and drop-in files, reloads the daemon, and proceeds with the upstream service lifecycle.

5. **Multiplexed Gateway Awareness**:
   - In environments where a single multiplexed gateway manages all profiles, OMES recognizes the shared gateway and applies the drop-in configuration without creating redundant individual profile units.
